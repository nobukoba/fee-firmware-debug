# HR-TDCのリセット方式をLR-TDCで比較

**Language: [English](README.md) | 日本語**

調査日：2026年10月20–21日（JST）。操作したのは問題基板`.16`のみ。正常基板`.11`は全試験を通してOFFを維持した。ジッタークリーナーは無効（`CDCE_PDB='0'`）。最後は既存対策F402へ戻し、`.16`とネットワークスイッチをONにしている。

CPLLロック確認・上位回路の待機だけを追加したF511は、接続状態の電源投入が **0/3** で改善しなかった。PHYを早めに起動する方式も加えたF512は **18/18**、PHY早期起動だけの1行版F503は **18/18**。1枚での有限回の結果であり、全基板の起動保証や故障部品の特定ではない。

## 結果

| 版 | 内容 | スイッチONで基板起動 | スイッチOFFから起動 | 正常時からスイッチOFF/ON |
|---|---|---:|---:|---:|
| F500 | 旧LRロジックの再ビルド | 3/21 | 3/3 | 5/5 |
| F402 | 既存の再初期化対策 | 24/24 | 12/12 | 15/15 |
| F511 | CPLL確認・上位リセット待機のみ | 0/3 | 3/3 | 3/3 |
| F512 | HR参考：PHY早期起動＋上位待機 | 18/18 | 3/3 | 15/15 |
| F503 | PHY早期起動のみ・1行変更 | 18/18 | 3/3 | 15/15 |

数字は成功回数／試行回数。旧LRロジックF500では、起動失敗状態から基板電源を変えずスイッチだけをOFF/ONして **1/1** 復帰した。同じFlashから電源を保持したままFPGAを再構成すると **4/4** 成功し、そのうち1回は無応答状態から復帰した。正常起動した後の30分通信監視も通過した。運転継続の正常性と、電源投入時の成功率は別の問題だった。

F402は、旧LR版の前、F511の後の対照試験、調査終了時に確認している。各試験群は[結果JSON](results.json)で分けて保存した。FPGAの再構成ではI/Oの初期値や接続モジュールの条件も変わるため、FPGA内部と外部の影響を一意に分離する実験ではない。

最初の旧LR接続起動群は **3/18**。F503試験後に旧LR版へ戻し、時間経過の対照として接続起動を再確認した結果は **0/3**。表は両時期を合計している。[再確認の計画](planned-native-reversal.json)はF503の起動結果を見る前に記録した。温度の直接測定・制御はしていない。

## 変更内容

LR元ソース：[StrLrTdc 5ac5ce7](https://github.com/AMANEQ-official/StrLrTdc/tree/5ac5ce75944aaec1ab2d4e81588aa9ab19eb7039)。HR参照：[StrHrTdcBase 33e3f35](https://github.com/AMANEQ-official/StrHrTdcBase/tree/33e3f35dfc43b04672d0bf6b352be2ff33b5579d)。

LRの`hdl/common`は[common-src 784244d](https://github.com/AMANEQ-official/common-src/tree/784244da3c0a60535bde74ac01daeadd8d4fe80a)サブモジュール。配布パッチはLF改行とした。固定したroot／commonのファイルを持つ一時インデックスへの順方向適用、逆方向適用、実際のビルド元との改行正規化後の一致を確認した。調査用の小さな候補ディレクトリは共通プロジェクトのファイルを再利用しており、それ単独では完全なクリーンチェックアウトではない。

- **F511**：[差分](f511-functional.patch)。AMANEQ側ラッパーから既存CPLLロックを取り出し、`ASYNC_REG`指定の3段FFで同期し、既存`SystemReset`でEthernet上位回路の解除を待つ。PHYは従来の約2.147秒の初期待機を維持。コメントを含め**追加26行／削除5行、2ファイル**。
- **F512**：[差分](f512-functional.patch)。さらに、有効なPCS/PMAのリセットをSYSロック後に解除し、上位リセットの起点も同じraw resetへ変更。上位待機は前提条件成立後に約4.295秒＋解除用32段。**追加27行／削除6行、2ファイル**。
- **F503**：[差分](f503-functional.patch)。有効なPCS/PMAの`reset => pwr_on_reset`を`reset => raw_pwr_on_reset`へ変えるだけ。上位回路は従来の待機を維持。**既存1行の置き換え**。
- **F402**：[以前の採用候補](../amaneq-side-minimum-20261019/README.ja.md)。機能上は3行追加＋既存1行変更。早期起動の後、起動中に1回再初期化する。生成IP内部は変更しない。

試験用バージョンIDと共通の基板クロック設定は、上記の機能差分の行数に含めない。全版でEthernet基準156.25 MHz、回線1.25 Gbps、SYS 125 MHz、独立クロック200 MHzを共通にした。本比較の各版間では、生成LR Ethernet IP内部とTDCのリセットロジックを同一のまま維持した。常時パワーダウン設定の未使用共通QPLLに対する不要なリセット接続変更は、F512/F503のビルド開始前に除去した。

変更した`reset`はPCS/PMAラッパーの入力。既存のGT内部リセット手順を早く開始する変更であり、SYSロック時に`GTRXRESET`を直接0へ固定する変更ではない。

固定したLRコミットの作業ツリーに、候補を**1つ選んで**適用する。例：`git submodule update --init --recursive`でサブモジュールを用意し、`git apply --check f503-functional.patch`、`git apply f503-functional.patch`を使う。F511/F512は`hdl/common`内も変えるため、結合パッチに親リポジトリの`git apply --index`を使わない。上流へコミットする場合はcommon-src側を別にコミットし、親のgitlinkを更新する。F503は親のtopだけを変える。パッチには共通クロック前提と試験用IDを含めないため、通常のAMANEQビルド手順と[以前の基板クロック確認](../amaneq-side-minimum-20261019/evidence/outerreset-f402-board-clock-audit.json)に従い、タイミング／DRCを再確認する。複数の候補を重ねて適用するものではない。

HRは10G PCS/PMA・QPLL、LRは1G PCS/PMA・CPLLを使う。今回は読める範囲の**リセット方針**を移したもので、HRコア全体やジッタークリーナー手順の移植ではない。クリーナー無効の指定に合わせCDCEロック条件は使わない。再利用モジュールの`masterReset`出力は未接続にし、PHYが確立すべきPLLロックでPHY自身をリセットし続ける帰還は作らない。

## 解釈と限界

上位回路の待ち時間だけではなく、**入力リンクに対するPHY初期化の時点**を調べる根拠が得られた。F503は、今回の`.16`で追加上位リセット回路が必須かを分ける比較であり、HRとLRの違いすべてを説明するものではない。

物理的な引き金は未確定。電源・基準クロックの過渡現象、受信獲得／アライメント、配置配線による余裕の違いなどが残る。今回の通常試験イメージではGTのCPLLロックや回復クロックの波形を新たに測っていない。FPGA構成レジスタの`PLL_LOCK`はGT CPLLの観測値ではない。失敗時に採取した構成レジスタではDONE/EOS成立、CRC／fallback異常なしだったが、正常受信を証明するものではない。

各版は別々に合成し、同じF402チェックポイントを参照するincremental配置配線を使った。名前で抽出したPCS/PMA部分のF500対F503比較では、プリミティブ種別／LOC／BELが **1596/1596**、ネットのROUTE／接続ピンが **2696/2701** 一致した。名前が明示的な共有定数、ROUTE文字列が10万文字を超える共有／大規模配線、外部リセットネット、抽出部分外のクロック配線は除外する。これは範囲を限定した配線比較で、全イメージの一致や影響する全経路を固定した比較ではない。個数と比較部分を正規化した署名ハッシュは[結果JSON](results.json)に記録した。

共通名の差5件と、各版だけにある別名5件ずつは、確認した範囲ではリセット関連だった。比較したコアのデータ経路は配置配線を大部分共有し、意図したリセット接続に差がある。抽出範囲内で配置配線の交絡を絞る結果だが、アナログ部品の故障を特定するものではない。

[Tcl署名生成関数](tools/pllwait_core_signature.py)と[ストリーム比較スクリプト](tools/compare_pllwait_core.py)に比較方法を残した。ローカルのVivadoチェックポイント／署名ファイルと調査時のディレクトリ構成が必要で、これらのツールは実機操作を行わない。

**F503を全基板向けの修正として扱わない。** 以前の同等1行版F403は`.16`が3/3でも正常`.17`が1/3だった。[以前の失敗と復元比較](../amaneq-side-minimum-20261019/README.ja.md#1行変更f403は不採用)。当時はOFF指定5秒の2回が失敗し、120秒の1回は成功した。今回の`.11`は指定どおり試験せず、終了時はF402へ戻した。

LR内部の500 nsタイマーには、既に`SOFT_RESET`で再待機する処理があり、安定クロック設定も5 nsだった。「ソフトリセット時の待機がない」ことはHR/LRの差として確認されていない。[ソース確認](hr-source-review.json)、[F503試験前に記録した予測](hypotheses-after-F512-before-F503.json)。

## 検証方法

Flashは操作ごとに全16 MiBをバックアップ・読戻しし、書き込みイメージと消去済み残領域を照合した。実際のコンパイル元、配線後タイミング、bus skew、DRC、物理クロック設定、同期回路が3個のFFとして残ることを確認した。デジタルシミュレーションではロック未成立・中断・リセット再投入・解除を確認したが、アナログCDRモデルではない。試作F501/F502は提案した同期ヘルパーの一部がSRLへ合成されたため、実機書き込み前に不採用とし、F511/F512では明示的にFFを保持した。

Flash書き込み直後は、電源を入れ直すまでFPGA上で書き込み用ヘルパーが動いている。その時点の初回無応答確認はファームウェアの起動失敗に数えず、電源操作を完了した試行だけを数えた。

最初の記録処理に`time`引数の重複エラーがあり、試行開始前に停止したログが1件ある。OFF/ON試行は行われず、正常`.11`のOFFも維持した。0試行の中断記録として別に保存し、ファームウェアの失敗には数えない。F402-r1開始前に記録処理を修正した。

合成時にはF500から共通するクロック名警告がある。最終F512/F503チェックポイントで必要なクロックと有効な非同期クロックグループを別途確認した。TDCグループ名一覧の`ckl_tdc2`という既存綴りを含め、制約は比較間で共通のまま維持した。タイミング結果は既存制約下の結果であり、TDC全体のタイミング／校正の承認ではない。

基板電源試験はOFF待機指定10秒＋遠隔制御の遅延。温度を管理した冷却試験ではない。HS3は接続したままで、電源レールの放電は実測していない。スイッチOFF起動はスイッチを切ってから基板をOFF/ONし、基板ON後15秒待ってスイッチをONにする。スイッチ単独試験では基板電源を維持し、スイッチをOFF指定10秒の後にONへ戻す。スイッチOFFはEthernetリンクの断を確認する条件であり、ローカルSFPのシリアル出力が無信号になることまでは保証しない。

active ARP試験群は最後のON確認後15秒待って、RBCPのファームウェアID・実行時IP・EEPROM比較領域128バイトのハッシュ不変・TCP 24番を確認する。5秒間隔で2回の成功を要求し、基板起動は120秒、リンク操作は180秒を観測期限の指定値にした。通信呼び出しの待ちや失敗時の状態取得により、記録上の試行区間は延びる場合がある。最初の旧方式F402試験群は早めにWindows ARPだけで探し始めているため、active ARP群との起動時間比較には使わない。閉じたパケットキャプチャーと試験区間を照合し、全失敗区間で実際の対象ARP要求を確認し、**21/21** の失敗区間ではARP応答がなかった。通信の成功・失敗はARPだけでなく、RBCP／TCPの全確認で判定する。生キャプチャー、Flashダンプ、認証情報、機器シリアル番号は公開しない。

電源操作なし・5秒間隔の通信監視：

| イメージ | 監視指定時間（分） | 確認回数 | 失敗 |
|---|---:|---:|---:|
| 0x60C4F402 | 30 | 359 | 0 |
| 0x60C4F402 | 5 | 60 | 0 |
| 0x60C4F500 | 30 | 359 | 0 |
| 0x60C4F512 | 15 | 180 | 0 |

検証範囲はネットワーク起動・復帰と低負荷のRBCP/TCP通信。TDC精度やフルDAQ運転の確認ではない。ハッシュ・各試行結果・パケット数は[結果JSON](results.json)、バイナリー成果物はローカルに保存した。
